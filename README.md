# Joint Flow Matching Enables Continuous Dose-Conditioned Cell Morphing

**Accepted at the ECCV 2026 Workshop on Bioimage Computing (BIC).**

Official implementation of our joint flow matching approach for continuous
dose-conditioned single-cell image generation. We train a VAE to compress
microscopy images into a shared latent space, then train one flow matching
model per drug compound over the joint distribution `p(z, c)` of cell
latents `z` and drug concentration `c`, using a dual-timestep formulation
(separate timesteps for `z` and `c`). Because sampling is a deterministic
ODE, the model is invertible: a real control cell can be encoded, inverted
to noise, and re-generated at any target concentration, producing
continuous dose-response morphs of a single source cell.

## Repository structure

```
config/
  vae_microscopy.yaml         # VAE training config
  latent_flow_joint.yaml      # joint flow matching training config (one drug at a time)
  *_sample.yaml                 # variants of the two configs above, using the small real sample_data/
metadata/
  cell_lines_drug_compounds.csv   # single-cell image metadata (relpath, drug, concentration, split, ...)
  sample_metadata.csv          # metadata for sample_data/, generated by scripts/build_sample_metadata.py
sample_data/                  # small curated subset of REAL images, included
experiments/                  # training runs are written here (created at runtime)
scripts/
  build_sample_metadata.py     # builds metadata/sample_metadata.csv from images placed in sample_data/
  download_checkpoints.py      # fetch pretrained checkpoints from the Hugging Face Hub
src/
  vae.py                       # MicroscopyVAE (encoder/decoder)
  flow_model.py                # JointFlowUNet: dual-timestep [z, c] velocity network
  dataset.py                   # dataset classes for VAE and joint flow training
  vae_trainer.py                # VAE trainer
  joint_flow_trainer.py         # joint flow matching trainer
  utils.py                      # experiment setup, checkpoint loading, plotting helpers
train_vae.py                  # train the microscopy VAE
evaluate_vae.py                # test-set reconstruction quality (PSNR / SSIM / MSE)
train_latent_flow_joint.py     # train the joint flow matching model for one drug
evaluate_latent_flow_joint.py  # FID/KID + dose-conditioned morph generation
```

## Installation

```bash
pip install -r requirements.txt
```

## Pretrained models

Trained checkpoints (one VAE, one flow model per drug) are hosted on the
Hugging Face Hub rather than in this repository, since binary weight files
don't belong in git history. `huggingface_hub` isn't in `requirements.txt`
since only `scripts/download_checkpoints.py` needs it — install it pinned
below `1.0` so it doesn't upgrade `transformers`'s own `huggingface-hub`
dependency out from under it in the same environment (`transformers`
requires `huggingface-hub<1.0`):

```bash
pip install "huggingface_hub<1.0"
python scripts/download_checkpoints.py --repo_id leabogensperger/joint-flow-matching-cells --vae
python scripts/download_checkpoints.py --repo_id leabogensperger/joint-flow-matching-cells --drug C7
# or: --all for the VAE + every drug's flow model
```

This downloads into `experiments/microscopy_vae/pretrained/` and
`experiments/latent_fm_joint_conc/pretrained_<drug>/`, so e.g.
`python evaluate_latent_flow_joint.py --exp latent_fm_joint_conc/pretrained_C7 ...`
works immediately.

### Evaluating the downloaded checkpoints

The full private dataset these were trained on isn't public yet (see
[Data](#data) below), so point the evaluation scripts at the small real
`sample_data/` bundled in this repo instead — both accept `--data`/
`--data_root` to override what's baked into the checkpoint's own config:

```bash
python evaluate_vae.py --exp microscopy_vae/pretrained \
    --data metadata/sample_metadata.csv --data_root sample_data
```

```bash
python evaluate_latent_flow_joint.py --exp latent_fm_joint_conc/pretrained_C7 \
    --data metadata/sample_metadata.csv --data_root sample_data --skip_fid
```

## Data

The dataset itself is **not** included in this repository (it is not yet
public). As soon as it is released, this repository will be updated.
What's included is the metadata (`metadata/cell_lines_drug_compounds.csv`)
describing every single-cell image crop, one row each:

| column          | description                                                |
|------------------|-------------------------------------------------------------|
| `relpath`        | image path *relative to* `data_root` (see below)            |
| `filename`        | image filename                                               |
| `label`           | cell line (e.g. `ONS76`)                                     |
| `drug`            | compound name, or `DMSO` for solvent controls                |
| `concentration`   | drug concentration in µM (`0.0` for DMSO)                    |
| `filtered`        | whether the image passed quality control                     |
| `split`           | `train` / `val` / `test`                                     |

Every config file has a `data_root` field, e.g.:

```yaml
data: "metadata/cell_lines_drug_compounds.csv"
data_root: "/path/to/your/dataset"
```

At load time each image is opened from `os.path.join(data_root, row['relpath'])`
— absolute or machine-specific paths never need to appear in the CSV, so it's
safe to keep the CSV in this repo while the underlying images live wherever
you keep the actual dataset. Set `data_root` to wherever you've placed a copy
of the dataset (its subfolder layout must match the `relpath` column, i.e.
`data_root/<setting>/<filename>`).

### Trying it out on a small real sample

`sample_data/` is a small curated subset of **real** images (275 single-cell
crops: DMSO plus all concentrations of C7 and CK-666, the two drugs in the
main paper text — see `sample_data/README.md`), included directly in this
repo so the whole pipeline below can run end to end with nothing else
needed. To extend or rebuild it, copy more real images into
`sample_data/<setting>/<filename>` (preserving the folder-per-condition
structure used by the real dataset) and re-run:

```bash
python scripts/build_sample_metadata.py
```

which looks each file up in `metadata/cell_lines_drug_compounds.csv` and
regenerates `metadata/sample_metadata.csv` with the matching real labels/splits.

## Running the pipeline

Four steps: train the VAE, sanity-check its reconstructions, train a flow
model on top of it for one drug, then evaluate that flow model. These use
the bundled `sample_data/` (see above), so they run with no setup beyond
[Installation](#installation) — each checkpoint's own `config.yaml` records
`data`/`data_root`, so steps 2 and 4 automatically evaluate on the same data
the checkpoint was trained on, no extra flags needed.

**1. Train the VAE** (jointly on every condition in `sample_data/`, so the
flow model in step 3 shares a common latent space):

```bash
python train_vae.py --config config/vae_microscopy_sample.yaml
```

Writes a run directory to `experiments/microscopy_vae_sample/<timestamp>/`,
containing `config.yaml` and `best_model.pth`. Takes the `--config` flag
only; everything else (epochs, batch size, loss weights, ...) comes from the
config file — edit it directly to change hyperparameters.

**2. Test the VAE** — reconstruction quality (PSNR / SSIM / MSE) on held-out
data, plus a saved grid of example reconstructions:

```bash
python evaluate_vae.py --exp microscopy_vae_sample/<timestamp>
```

`<timestamp>` is the run directory from step 1. Results land in
`experiments/microscopy_vae_sample/<timestamp>/evaluation_best_model/`.

**3. Train the joint flow model** for a single drug (one model per
compound, matching the paper's setup). First point `vae.checkpoint` in
`config/latent_flow_joint_sample.yaml` at the checkpoint from step 1
(`experiments/microscopy_vae_sample/<timestamp>/best_model.pth`):

```bash
python train_latent_flow_joint.py --config config/latent_flow_joint_sample.yaml --drug C7
```

Repeat per drug (`sample_data/` also has CK-666: `--drug CK-666`) — each run
is an independent model. Writes to
`experiments/latent_fm_joint_conc_sample/<timestamp>_<cell_line>_<drug>_log10/`,
containing `config.yaml`, `best_model.pt`, and `latent_scale.pt`.
`--cell_line` can also be overridden the same way.

**4. Evaluate the joint flow model** — dose-conditioned morph generation by
inversion of real control cells across concentrations. Pass `--skip_fid`:
`sample_data/` has too few images per concentration for a statistically
meaningful FID/KID (that part of the script is meant for the full dataset —
see [Running against your full dataset](#running-against-your-full-dataset)
below):

```bash
python evaluate_latent_flow_joint.py \
    --exp latent_fm_joint_conc_sample/<timestamp>_<cell_line>_<drug>_log10 \
    --skip_fid
```

`<timestamp>_<cell_line>_<drug>_log10` is the run directory from step 3.
Results land in
`experiments/latent_fm_joint_conc_sample/<timestamp>_<cell_line>_<drug>_log10/evaluation/`.

### Running against your full dataset

Same four steps, same commands, with two changes: use `config/vae_microscopy.yaml`
/ `config/latent_flow_joint.yaml` (the non-`_sample` configs) in place of the
sample ones, and set `data_root` in each to wherever your copy of the
dataset lives (see [Data](#data) above) before running — everything else in
those configs already matches the paper's settings. Step 4's FID/KID also
needs an offline Inception-v3 checkpoint and `--inception_path` — see
[Offline Inception weights](#offline-inception-weights) below.

## Offline Inception weights

FID/KID require Inception-v3 features. `torchvision` normally downloads the
pretrained weights on first use, but our training/eval cluster had no
internet access, so the weights need to be fetched ahead of time on a
machine that does have internet access and copied over:

```bash
# on a machine with internet access
python -c "from torchvision.models import inception_v3, Inception_V3_Weights; \
    inception_v3(weights=Inception_V3_Weights.IMAGENET1K_V1)"
# the checkpoint is cached at ~/.cache/torch/hub/checkpoints/inception_v3_google-0cc3c7bd.pth
```

Copy that file to the offline machine and pass its path via
`--inception_path`.
